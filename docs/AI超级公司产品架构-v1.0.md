## 0. 一页纸

**一句话产品定义**：把公司里可标准化的活，装进一个以 **工作单（Ticket）** 为最小单位、以 **数字员工（角色化 Agent）** 为执行主体、以 **人验收** 为质量闸门的操作系统——让一个管理者能同时盯住几十条并行工作流。

**产品骨架（四平面 + 五域）**：

```
+----------------------------------------------------------------------------+
| 体验面   IM(飞书/钉钉/企微)  ·  Web 控制台  ·  开放 API  ·  报表推送            |
+----------------------------------------------------------------------------+
| 产品域   工作台  ·  组织(数字员工)  ·  编排  ·  记忆  ·  治理                  |
+----------------------------------------------------------------------------+
| 控制面   工作总线(Ticket 状态机)  ·  路由调度  ·  权限策略  ·  计量预算         |
+----------------------------------------------------------------------------+
| 执行面   数字员工运行时  ·  模型网关  ·  工具网关(MCP)  ·  沙箱                |
+----------------------------------------------------------------------------+
| 数据面   工单库  ·  交付物  ·  记忆库  ·  审计事件  ·  成本账                  |
+----------------------------------------------------------------------------+
```

**三个判断**（决定这个产品值不值得做）：

1. **客户买的不是"更聪明的 Agent"，而是"可验收的产能"。** 验收体验决定续费；把验收压到 5 分钟以内，产品才成立，否则人只是从"干活"变成"审活"，产能不涨。
2. **入口必须长在客户已经在工作的地方（IM），否则激活率上不去。** 控制台只服务管理与治理，不承担日常高频操作。
3. **记忆是复购理由。** 没有组织记忆，第二年仍要从零调教，产品退化成项目制交付。

**MVP 只做三件事**：一条 IM 入口 → 一张工作单 → 一屏验收（带证据、可审计、计成本）。

**P0 成功判据**：一个真实部门、一条真实流程、**W1–W8 连续 8 周**、累计 ≥200 单、一次通过率 ≥75%、验收**中位数 ≤3 分钟/单、P90 ≤5 分钟**、单均全成本 ≤ 纯人工的 60%。

**需要先拍板的事（6 项，见 11.2 节）**：首批客户是自用还是对外售卖；MVP 入口选飞书还是钉钉；计费按"在岗数字员工数"还是"工作单量"（详见第 11.2 节）。

## 1. 产品定位

### 1.1 判别标准：三个阶段，三种产品

行业里"AI 超级公司"已有相对稳定的阶段划分。阿里云研究院《2025 AI 超级公司白皮书》将其描述为"AI 增强型 → 人机协同型 → 智能液态型"三阶段演进（[阿里云研究院白皮书](https://www.aliyun.com/reports/2025-ai-supercompany)）；飞书 8.0 等协同办公产品把 Agent 直接嵌进 IM 与文档（[飞书 8.0 发布](https://tech.cnr.cn/techph/20260915/t20260915_527814511.shtml)）。这些是行业参照，不是本文结论。

真正决定产品形态的，是**谁在执行、谁在负责**：

| 维度 | AI 增强型 | 人机协同型（本产品目标） | 智能液态型（远期） |
| --- | --- | --- | --- |
| 执行主体 | 人，AI 辅助 | 数字员工为主，人验收与例外处理 | Agent 网络自组织 |
| 人的角色 | 操作者 | 目标设定者、验收人、例外裁决者 | 目标与红线设定者 |
| 质量机制 | 人工复核 | 评测集 + 验收 + 抽检 + 审计 | 自动验收 + 红队 + 事后审计 |
| 扩张方式 | 招人、买软件 | 增加角色与算力 | 动态组队、按需扩缩 |
| 软件形态 | 功能菜单 + Copilot | **工作单总线 + 角色编制** | 液态任务市场 |
| 管理半径 | 5–10 人 | 一人 20+ 条并行工作流 | 一人管一片智能体网络 |

> 本产品定位在**第二阶段的工程化落地**：既不做"给现有软件加个对话入口"的增强型工具，也不承诺"全自动公司"。

### 1.2 产品是什么 / 不是什么

| 是 | 不是 |
| --- | --- |
| 一个**工作中枢**：所有输入归一成单，所有执行留下证据 | 一个"万能助手"，什么都能聊、什么都不负责 |
| 一个**数字员工编制系统**：角色卡 = 岗位说明书 + 权限 + 预算 | 一个提示词市场或 Agent 商店 |
| 一个**验收与审计系统**：一屏看结论、证据、成本、风险 | 一个只产出内容、不承担结果的内容工具 |
| 一个**组织记忆系统**：结论、决策、SOP 可检索、可纠错 | 一个把聊天记录全量塞进向量库的"知识库" |
| 一个**风险分级授权系统**：默认 L1 + 封顶 R1 自主，R2 逐次审批，R3 永不授权 | 一个默认全自动、出事再补权限的自动化平台 |

### 1.3 竞争位

| 类别 | 代表形态 | 它解决什么 | 它的边界 | 本产品的差异 |
| --- | --- | --- | --- | --- |
| 低代码 Agent 平台 | Coze、Dify、扣子类 | 快速搭出一个能对话/调工具的 Agent | 停在"造 Agent"，不管谁接单、谁验收、成本归谁 | 以**工作单**为中心，Agent 只是执行者 |
| 企业 Copilot | 飞书 aily、钉钉 AI 助理、M365 Copilot | 在人现有工作流里做辅助 | 人仍是执行主体，无法承接整段流程 | 以**交付与验收**闭环为中心 |
| RPA / 工作流引擎 | UiPath、审批流引擎 | 规则明确的重复动作 | 规则一变就脆，无法处理语义判断 | 语义驱动 + 可泛化 + 有人兜底 |
| 垂直 Agent 套件 | 客服/销售/招聘垂类 SaaS | 单点场景开箱即用 | 场景固化，跨部门协同弱 | 跨系统、跨部门的通用工作中枢 |
| 自研脚本 + 大模型 API | 内部工具 | 便宜、灵活 | 无治理、无记忆、无审计，难以规模化 | 治理与记忆是产品本体 |

**定位一句话**：*别人卖"造 Agent 的工具"，我们卖"管数字员工干活的系统"。*

### 1.4 价值主张

```
对 CEO：      把"人头预算"换成"产能预算"——按单计价，看得见单位成本
对业务主管：  把流程交出去，把验收留下来——管辖半径从 10 人扩到 20+ 条工作流
对一线员工：  不用学新系统，在 IM 里说一句就有人接单
对 IT/风控：  每个动作有权限、有额度、有留痕、可回放
```

**明确不做**（写进产品边界，防止需求蔓延）：

| 不做 | 原因 |
| --- | --- |
| 通用大模型训练/微调 | 不是差异化，且资本开支不可控 |
| 通用 BI / 数据仓库 | 已有成熟品类，做集成而非替代 |
| 全自动无人公司 | 风险不可控，客户也不会买"无人担责" |
| 复杂可视化流程编排器 | MVP 阶段用配置 + 模板，画布是 P2 |
| 自建 IM | 寄生在客户已有的 IM 上 |

## 2. 用户与场景

### 2.1 五类角色与他们的 JTBD

| 角色 | 是谁 | 核心任务（JTBD） | 关键诉求 | 使用频率 |
| --- | --- | --- | --- | --- |
| 经营负责人 | CEO / 总经理 / 事业部负责人 | 用更少的人承接更多业务量 | 看板：产能、成本、质量、风险 | 每日 5 分钟 |
| 流程负责人 | 部门主管 / 业务专家 | 把流程交给数字员工并保证结果 | 建角色、定验收标准、处理例外 | 每日 30–60 分钟 |
| 验收人 | 业务骨干 / 质检 | 快速判断交付物能不能用 | 一屏看到结论 + 证据 + 风险 | 高频，按队列 |
| 一线员工 | 销售 / 客服 / 运营 | 把自己的活派出去、拿到结果 | 在 IM 里提单、追问、催办 | 高频 |
| 平台/风控 | IT、安全、财务 | 权限、预算、审计、合规 | 策略配置、异常告警、账单 | 每周 |

> 产品设计的分歧点常在"验收人"：他既是产品最大的使用者，也是规模化的瓶颈。**验收体验是本产品的第一优先级，高于 Agent 能力。**

### 2.2 三个关键时刻（决定留存）

**① 早上 9:00，经营负责人打开看板**

```
昨晚 → 今早
┌─────────────────────────────────────────────────┐
│ 昨日完成 128 单 ｜ 一次通过 91% ｜ 节省 34 人时 │
│ 待我决策 2 单（超额度 / 政策冲突）              │
│ 异常：退款角色升级率上升 8% → 查看原因          │
└─────────────────────────────────────────────────┘
```

价值：**从"问进度"变成"看事实"**。没有这块，管理者不会每天回来。

**② 上午 10:00，主管在 IM 里收到一张验收卡**

```
┌────────────────────────────────────────────────┐
│ 结论：订单 #88213 符合 7 天无理由，退款 ¥328   │
│ 证据：订单快照 · 政策 v3.2 第 4 条 · 用户原话  │
│ 成本：¥0.42 ｜ 耗时 48s ｜ 风险 R2（已限额内） │
│ [通过] [驳回并说明] [转人工] [看完整过程]      │
└────────────────────────────────────────────────┘
```

价值：**验收 30 秒完成**。这是产品最核心的交互，必须做到"不打开第二个页面就能决策"。

**③ 下午 3:00，一线员工在群里 @数字员工**

```
员工：@退款专员 这单用户说没收到货，能退吗？
数字员工：已核对物流（已签收）与聊天记录，建议部分退款 ¥120，
          依据《售后政策 v3.2》第 6 条。需要我发起吗？
员工：发起。
数字员工：已发起，单号 RF-20261102-019，预计 2 小时到账。
```

价值：**零学习成本**。入口即产品。

### 2.3 首次价值时间（TTFV）路径

```
注册/开通 → 接入 IM(10 分钟) → 选一条模板流程 → 上传 20 条历史样本
   → AI 生成角色卡草稿 + 验收标准 → 人工修改 15 分钟
   → 单条试跑 + 人工验收
   TTFV 目标：≤ 1 个工作日拿到"第一条人工验收通过的单"
```

> 这 20 条样本只够"试跑"，不构成 7.2 节要求的 ≥50 条评测金标。正式上岗（影子 → 灰度）发生在 TTFV 之后；两者混谈会让承诺的 TTFV 被评测流程击穿。

**采用漏斗与典型流失点**：

| 阶段 | 流失原因 | 产品对策 |
| --- | --- | --- |
| 开通 → 接入 IM | 需要管理员权限、配置复杂 | 提供一键安装包 + 权限清单 |
| 接入 → 首单 | 不知道从哪条流程开始 | 内置 6 个行业模板，默认选"知识问答" |
| 首单 → 第 20 单 | 验收太慢、结果不稳定 | 验收一屏 + 影子模式先建信任 |
| 第 20 单 → 日常 | 只当玩具，没进 KPI | 看板对接周会，成本与产能上墙 |

## 3. 产品形态与信息架构

### 3.1 三个入口的分工

| 入口 | 承载 | 为什么 | 优先级 |
| --- | --- | --- | --- |
| IM 原生（飞书/钉钉/企微） | 提单、追问、验收卡、告警、日报推送 | 员工不装新软件；消息天然带上下文与责任人 | **P0** |
| Web 控制台 | 角色管理、编排配置、记忆治理、审计、账单、看板 | 管理动作低频但复杂，需要表格与详情 | P0（MVP 精简版） |
| 开放 API / Webhook | 系统对接、批量建单、嵌入自有系统 | 企业客户必须能集成 | P1 |

**原则**：**IM 是入口，不是界面。** 所有需要"比较、配置、追溯"的动作回控制台；所有"通知、确认、一句话决策"留在 IM。

### 3.2 五个产品域

```
                    +---------------+
                    | 工作台 Workbench |
                    +--------+-------+
          +----------+--------+-------+----------+
          v          v                v          v
   +-----------+ +-----------+ +-----------+ +-----------+
   |组织        | |编排        | |记忆        | |治理        |
   |Organize   | |Orchestrate| |Knowledge  | |Govern     |
   |角色/编制   | |触发/路由   | |条目/技能   | |权限/预算   |
   |评测        | |SLA        | |纠错        | |审计        |
   +-----+-----+ +-----+-----+ +-----+-----+ +-----+-----+
         +-----------+-----+-------+-----------+ 
                             v
                    +---------------+
                    | 平台底座        |
                    | 模型/工具/计量  |
                    +---------------+
```

> 读图：上端是入口（我提的单 / 待我验收 / 例外），下端是共享底座（模型网关 / 工具网关 / 沙箱 / 计量）；五个域横向平级，任何域都不能绕过控制面直连数据面。

- **工作台**：所有人每天打开的界面，回答"有什么要我处理"。
- **组织**：数字员工的招聘、上岗、绩效、扩权、退休。
- **编排**：输入从哪来、怎么变成单、派给谁、多久必须完成。
- **记忆**：组织知识与经验的沉淀、检索、纠错。
- **治理**：谁能做什么、花多少钱、留下什么痕迹。

### 3.3 信息架构（IA 树）

```
AI 超级公司 OS
├─ 工作台

├─ 编排

│  ├─ 触发器与路由规则

│  └─ 交付与回写规则
├─ 记忆
│  ├─ 知识域（按部门 / 流程划分）
│  ├─ 记忆条目（来源 / 置信度 / 有效期 / 纠错）

├─ 治理

│  └─ 合规与风险告警
```

### 3.4 页面清单与优先级

| 页面 | 目的 | 关键元素 | 优先级 |
| --- | --- | --- | --- |
| 待我处理 | 一屏清空今日决策 | 验收卡列表 + 批量操作 | P0 |
| 工作单详情 | 判断这单靠不靠谱 | 结论 / 证据链 / 工具调用时间线 / 成本 / 审计 | P0 |
| 角色卡编辑 | 定义数字员工 | 表单 + 自然语言生成草稿 | P0 |
| 单列表 | 全局检索与追溯 | 筛选（状态/角色/风险/成本） | P0 |

| 审计回放 | 事故复盘 | 时间线 + 上下文快照 + 决策点 | P1 |
| 路由规则 | 分派配置 | 规则表 + 模拟器 | P1 |
| 评测集 | 角色质量门禁 | 用例、通过率、回归对比 | P1 |
| 技能库 | 复用 | 技能卡 + 安装 | P2 |

## 4. 领域模型

### 4.1 对象关系

```
Workspace(租户)
├─ OrgUnit(部门/团队) ── 记忆域、权限域、预算域
├─ Human(人) ── 经营负责人 / 流程负责人 / 验收人 / 员工 / 管理员
├─ Role(角色卡) ──1:N── AgentInstance(在岗实例)
│      │                 └─ 工具白名单 · 数据域 · 额度 · 评测集 · 记忆域
│      └─ 版本化：每次扩权或改工具 = 新版本
├─ Trigger(输入事件) ─▶ Ticket(工作单) ──1:N── Assignment(执行)
│                            │                  ├─▶ Deliverable(交付物)
│                            │                  ├─▶ Approval(审批)
│                            │                  └─▶ Cost(计量)
│                            ├─▶ Review(验收) ─▶ 通过 / 驳回 / 转人工
│                            └─▶ MemoryRef(引用记忆)
├─ MemoryEntry(记忆条目) ── 来源 · 置信度 · 有效期 · 版本
├─ Policy(策略) ── 权限 · 额度 · 审批 · 脱敏
└─ AuditEvent(审计事件) ── 全量、只追加
```

### 4.2 核心对象

| 对象 | 职责 | 关键字段 | 生命周期 |
| --- | --- | --- | --- |
| Role 角色卡 | 数字员工的"岗位说明书" | 使命、边界、工具、数据域、额度、评测、记忆域 | 草稿 → 评测 → 影子 → 灰度 → 在岗 → 停用 |
| AgentInstance | 在岗的执行实体 | 角色版本、并发度、健康度 | 创建 → 运行 → 降级 → 回收 |
| Trigger | 一次外部输入 | 渠道、幂等键、原始载荷 | 收到 → 去重 → 建单 / 丢弃 |
| Ticket | 最小工作单 | 类型、优先级、风险、owner、SLA、预算 | new → triaged → (needs_info ↔ triaged) → assigned → in_progress → review → accepted / failed；中途可 blocked → in_progress |
| Assignment | 一次执行尝试 | 执行者、上下文快照、工具调用、成本 | 开始 → 完成 / 失败 / 超时 |
| Deliverable | 可验收的产出 | 类型、内容、证据引用 | 草稿 → 已交付 → 已采纳 / 已驳回 |
| Review | 验收决策 | 结论、意见、驳回原因 | 待验 → 通过 / 驳回 / 转人工 |
| MemoryEntry | 可复用的组织经验 | 类型（事实/程序/判断）、来源、置信度 | 候选 → 生效 → 失效 / 纠错 |
| Policy | 规则 | 作用域、条件、动作 | 草稿 → 生效 → 归档 |
| Cost | 计量 | token、工具调用、时长、金额 | 逐笔 → 归集到单 |

### 4.3 风险等级 × 自治等级（授权矩阵）

取值与《架构实现方案》4.2 节完全一致，产品上分层呈现：

| 自治等级 \ 风险 | R0 只读/草稿 | R1 内部可逆写 | R2 对外/资金/不可逆 | R3 高敏（法务/人事/安全） |
| --- | --- | --- | --- | --- |
| L1 建议 | 自主 | 建议，人执行 | 建议 + 人审批 | 禁止 |
| L2 执行 | 自主 | 逐次审批 | 逐次审批 + 双人 | 禁止 |
| L3 负责 | 自主 | 自主（留痕） | 节点审批 + 限额 | 禁止 |
| L4 经营 | 自主 | 自主 | 限额内自主，事后审计 | 禁止 |

**产品规则**：

- **R3 永远人做**：界面不提供"授权给数字员工"的入口，避免误开。
- 新建角色默认 **L1 且 max_risk=R1**；"扩权" = 提升 L 级或提高 max_risk，必须走 7.2 节扩权评审。
- 工作单详情页必须显示本单使用的自治等级与额度消耗——这是验收人的决策依据，也是审计证据。

### 4.4 五个不变量（架构级约束）

违反任意一条，产品就会退化成"套壳 Agent"：

| # | 不变量 | 违反后的后果 | 实现位置 |
| --- | --- | --- | --- |
| I1 | 每张单同一时刻只有一个责任人 | 多头负责 = 无人负责 | Ticket.owner 唯一约束 |
| I2 | 交付必须带证据（引用、调用记录、附件） | 无法验收、无法追责 | Deliverable 必填 evidence |
| I3 | 越权动作在执行前拦截，而非事后审计 | 一次越权即事故 | 工具网关 + 策略引擎 |
| I4 | 每笔成本可归集到单、到角色、到部门 | 算不出单位经济性 | 计量埋点强制 |
| I5 | 记忆必须有来源与置信度 | 错误经验污染全局 | MemoryEntry 必填 source |

## 6. 系统架构（产品视角）

### 6.1 四平面与依赖方向

```
体验面 ──▶ 控制面 ──▶ 执行面 ──▶ 数据面
  ▲           │           │           │
  └┘
        所有调用都必须经过控制面（鉴权/计量/留痕）
```

| 平面 | 职责 | 不允许做的事 |
| --- | --- | --- |
| 体验面 | 渲染、交互、通知 | 直接调用模型或工具 |
| 控制面 | 建单、路由、鉴权、策略、计量 | 承载长耗时任务 |
| 执行面 | 数字员工循环、工具调用、沙箱 | 绕过策略直接写外部系统 |
| 数据面 | 工单、交付物、记忆、审计、账 | 被业务逻辑直接改写 |

**关键约束**：执行面永远拿不到"长期凭证"，只拿控制面签发的**短期、限定范围**的令牌。这一条决定了产品能不能卖给风控严格的客户。

### 6.2 一次请求的跨平面时序

```
IM 消息
│① 体验面：接收、鉴权、识别意图│
  ▼
控制面：② 幂等去重 → ③ 建单（类型/风险/SLA/预算）→ ④ 选角色（技能+负载+权限）
│⑤ 签发执行令牌│
  ▼
执行面：⑥ 装配上下文（单 + 记忆 + 角色卡）→ ⑦ 规划 → ⑧ 调工具（网关鉴权/计量）
│⑨ 产出交付物  + 证据│
  ▼
控制面：⑩ 落库、计费、通知验收人
  ▼
体验面：⑪ IM 验收卡 → 人决策 → ⑫ 通过则沉淀记忆、驳回则返工
```

### 6.3 与现有 Harness 的映射（参考实现）

本机已运行一套与目标形态同构的原型（DSH Superagent），可作为 P0 的实现底座：

| 产品能力 | 原型现状 | 产品化差距 |
| --- | --- | --- |
| IM 入口 / 工作单 | 飞书触发 → 工单 → 执行 → 回报，已验证 | 缺多租户、缺可视化单详情 |
| 数字员工 | 角色化 Worker、独立工作区、可并行 | 缺角色卡管理界面与编制控制 |
| 工具网关 | CLI/API 调用、代码执行 | 缺统一鉴权、额度与审计埋点 |
| 记忆 | 跨会话检索（弱）、仓库内约定 | 需重建为带来源与权限的记忆服务 |
| 治理 | 仓库权限、人工合并、评审限额 | 需 RBAC + 预算 + 回放 |
| 计量 | 无 | 需从第一单开始埋点 |

> 结论：**P0 不需要重写底座，需要在现有 Harness 上补"产品壳"**：角色卡、验收一屏、计量与审计。详见《架构实现方案》第 13 章。

### 6.4 多租户与数据边界

| 隔离级别 | 适用客户 | 实现 | 成本 |
| --- | --- | --- | --- |
| 逻辑隔离（共享库，租户 ID） | 中小企业 SaaS | 行级隔离 + 加密 | 低 |
| 独立库/独立实例 | 中大型企业 | 每租户独立 schema | 中 |
| 私有化部署 | 金融、政务、大型集团 | 客户 VPC 内整套部署 | 高 |

**数据边界的三条硬规则**：

1. 记忆条目跨租户永不共享；跨部门共享需显式授权。
2. 模型调用默认不出境、不留存训练；敏感字段出网关前脱敏。
3. 审计事件只追加、不可改，保留期**默认 ≥1 年，涉资金/合同单 ≥5 年**，且不短于客户行业监管要求（与实现方案 9.4 一致）。

**数据迁移与退出**（企业客户必问，P0 就要有答案）：

| 事项 | 承诺 |
| --- | --- |
| 导入 | 支持从 Excel/CSV 导入历史工单作为评测样本；支持从现有 ITSM/工单系统批量建单 |
| 导出 | 工作单、交付物、审计日志可全量导出为 JSON + CSV，随时可下 |
| 退出 | 合同期满后 30 天内提供全量导出包；我方在导出确认后 60 天内删除生产数据（审计事件按合同保留期） |
| 模型切换 | 角色卡与提示词不绑定供应商，换模型不改配置 |

### 6.5 非功能指标（P0 目标）

| 指标 | 目标 | 说明 |
| --- | --- | --- |
| 建单延迟 | P95 < 2s | 从消息到工单可见 |
| 验收页加载 | P95 < 1.5s | 决定验收体验 |
| 单均执行时长 | < 5 分钟（异步可更长） | 长任务走异步 + 通知 |

## 7. 关键流程

### 7.1 一单到底

```
输入 ──▶ 建单 ──▶ 分派 ──▶ 执行 ──▶ 交付 ──▶ 验收 ──▶ 沉淀
││ │ │ │ ││
 幂等     风险定级  技能匹配  上下文装配  证据打包  一屏决策  记忆/指标
 去重     SLA/预算  负载均衡  工具调用    自检清单  驳回返工  成本归集
```

**产品要点**：

- 建单时必须给出**风险等级**，它决定默认自治度与是否需要审批。
- 交付物必须自带**自检清单**结果（缺字段、超额度、引用失效会在这里被拦）。
- 驳回必须选**原因码**（信息不足 / 判断错误 / 格式不符 / 越权），原因码驱动记忆纠错与评测集补充。

### 7.2 角色上岗（数字员工的"招聘—试用—转正"）

```
需求识别 ─▶ 角色卡草稿 ─▶ 评测集 ─▶ 影子运行 ─▶ 灰度 ─▶ 在岗 ─▶ 扩权评审
   │            │           │          │         │       │          │
  流程痛点   AI生成+人改  金标≥50条  只读比对   10%流量 SLA监控  连续4周达标
```

| 阶段 | 进入条件 | 退出条件 | 产品界面 |
| --- | --- | --- | --- |
| 草稿 | 有明确流程与验收标准 | 角色卡字段完整 | 角色卡编辑 |
| 评测 | 有 ≥50 条历史样本 | 通过率 ≥85%，安全项 100% | 评测集 |
| 影子 | 评测通过 | 30 单与人工比对一致率 ≥80% | 影子对比视图 |
| 灰度 | 影子通过 | 10% 流量下指标达标 | 灰度看板 |
| 在岗 | 灰度通过 | 持续达标 | 绩效页 |
| 扩权 | 连续 4 周达标 + 审计无高危 | 主管批准 | 扩权建议卡 |

### 7.3 例外升级（产品的"安全阀"）

```
执行中 ──┬─ 置信度低于阈值 ───────┐
         ├─ 金额/权限超限 ────────┤
         ├─ 政策冲突/无先例 ──────┼──▶ 升级到人（IM 卡片）
         ├─ 工具连续失败 ─────────┤         │
         └─ 用户要求转人工 ───────┘         ▼
                                 人裁决：放行 / 改派 / 终止
                                          │
                                          ▼
                                 裁决理由 ─▶ 记忆（判断类）
```

**产品要点**：升级不是失败，是**训练数据来源**。每一次人工裁决都应产生一条"判断类记忆"，下次同类情形优先复用。

### 7.4 失败与申诉（failed 单的客户可见处置）

失败不是终点，产品必须给出三条明确出口，否则客户会认为"这产品做不成事就跑"：

| 类型 | 判定 | 客户可见动作 | 计费 |
| --- | --- | --- | --- |
| 可重试 | 工具超时、模型抖动 | 系统自动重试 ≤2 次，界面显示"重试中" | 重试成本计入原单 |
| 需改信息 | 缺字段、附件缺失 | 退回提单人，原因码 + 缺什么 | 不计费 |
| 判定失败 | 多次失败或人工判定做不了 | **转人工**（人接管继续）或 **关闭并说明**；记入评测集 | 按已消耗实计 |

**申诉通道**：验收人不通过、但提单人认为应通过时，可发起二次裁决（上级或质检）。二次裁决结果反向修正该角色的评测集与记忆——**申诉数据是产品最贵的训练信号，必须采集**。

### 7.5 记忆沉淀与纠错

```
验收通过 ──▶ 提炼候选 ──▶ 去重/合并 ──▶ 人工确认（P0）──▶ 生效
                                    └┤
生效记忆 ──▶ 被引用 ──▶ 验收驳回 ──▶ 标记可疑 ──▶ 复核 ──▶ 修正/失效
```

| 记忆类型 | 例子 | 来源 | 有效期 |
| --- | --- | --- | --- |
| 事实 | 客户 A 的结算周期是月结 60 天 | 合同/工单 | 长，变更时失效 |
| 程序 | 退款审批需先核物流再核政策 | 流程文档/工单 | 中，政策变更时失效 |
| 判断 | 类似投诉优先补偿而非解释 | 人工裁决 | 中，需定期复核 |

**反模式**：把全部聊天记录灌进向量库。结果是检索噪声大、责任不清、越权泄露。**记忆以"条目"为单位，不以"语料"为单位。**

### 7.6 计费与审计

```
每次模型调用 / 工具调用 / 沙箱时长
        │
        ▼
 计量事件（tenant, ticket, role, unit, qty, cost）
        │
        ├──▶ 归集到单 ───▶ 单成本
        ├──▶ 归集到角色 ─▶ 单位产能成本
        └──▶ 归集到部门 ─▶ 月度账单 / 预算告警
```

**审计链**：`Trigger → Ticket → Assignment → ToolCall → Deliverable → Review → Memory`，任一环节可按单回放。客户问"这单为什么这么处理"，答案是**一条可点开的时间线**，不是一段解释。

| Business | 20 个角色、多部门、评测、审计回放 | 席位 + 单量 + 模型额度 | **¥1.5–3 万/月** | ≤3,000 单/月 |
| Enterprise | 私有化、SSO、定制连接器、SLA | 年费 + 实施 + 运维 | ¥50 万起/年 | 不限，按实例 |

**口径**：以上是**起价 + 规模上限**，不是"任意规模都按这个价"。8.3 节的 ROI 示例按 Business 档、3,000 单/月的**中位配置**取 ¥6 万/年（≈¥5k/月，年度预付折扣后），属起价区间的低价段；若客户达到上限单量，平台费应按合同阶梯上调。**价格页与 ROI 计算必须使用同一个价位，否则演示会被客户一眼算穿（评审已指出过这一点）。**

**定价逻辑**：客户的价值锚点是"省下的人力成本"，不是"token 成本"。因此定价必须落在**人头预算的 20–40%**，并明确"超出单量按包续购"。

> 备选方案：按"在岗数字员工数"计费（更像"雇人"），心理账户更顺，但与客户产能波动冲突，需二选一并在 P0 阶段验证。

### 8.3 ROI 模型（销售与产品共用）

```
年节省 = Σ(流程单量 × 单均人工分钟 × 人力分钟成本) − (平台费 + 模型费 + 验收人力成本)

回收期（月） = 一次性投入 ÷ 月净节省
健康线：回收期 < 6 个月；单均成本 < 纯人工 60%
```

| 参数 | 取值（示例） | 说明 |
| --- | --- | --- |
| 流程单量 | 12,000 单/年 | 1 个部门、1 条高频流程（约 48 单/工作日） |
| 单均人工分钟 | 12 分钟 | 需客户提供基线，禁止拍脑袋 |
| 人力分钟成本 | ¥2.5 | 按年薪 ÷ 年有效分钟折算 |
| 验收人力成本 | 单均 3 分钟 × ¥2.5 = ¥7.5 | 产品必须把验收压到 3 分钟以内 |
| 模型成本 | 单均 ¥1.2 | 随模型降价下降 |
| 平台年费 | ¥6 万/年 | Business 档低价段（3,000 单/月量级，见 8.2 口径） |
| 一次性实施 | ¥8 万 | 接入 1–2 个系统 + 首批角色建设 |

> 示例结论：毛节省 = 12,000 × 12 × 2.5 = **¥36 万/年**；扣除验收 ¥9 万、模型 ¥1.44 万、平台 ¥6 万后净节省约 **¥19.6 万/年**；一次性投入 ¥8 万，回收期约 **4.9 个月**；单均全成本 ¥13.7 ≈ 纯人工（¥30）的 **46%**。**参数必须用客户实测替换，禁止对外直接引用示例数字。**

**敏感性（验收分钟是最敏感参数，必须给区间而不是单点）**：

| 验收分钟/单 | 净节省（年） | 回收期 | 单均成本 | 占纯人工 | 判定 |
| --- | --- | --- | --- | --- | --- |
| 3 分钟（P0 目标） | ¥19.6 万 | 4.9 个月 | ¥13.7 | 46% | 健康 |
| 5 分钟（P0 上限） | ¥13.6 万 | 7.1 个月 | ¥18.7 | 62% | 超 60% 红线 |
| 8 分钟（实现方案旧口径） | ¥4.6 万 | 21.1 个月 | ¥26.2 | 87% | 不成立 |

**结论**：验收中位数必须做到 3 分钟，产品才有经济性；5 分钟时虽仍回本，但单均成本已越过 60% 红线。这就是"验收体验"被列为产品第一优先级（2.1 节）的原因。

> 平台费口径提醒：若按 Business 起价 ¥1.5 万/月（¥18 万/年）计，本示例净节省为 ¥+7.6 万——**该规模客户必须落在 ¥6 万/年量级的配置上**，销售须用 8.2 的规模上限表匹配档位，禁止用低价档打大客户。

## 9. 度量

### 9.1 北极星与指标树

**北极星：每周被验收通过的工作单数（Weekly Accepted Tickets, WAT）**

它同时反映"用了没有、做成了没有、信任了没有"，且无法靠堆量造假（因为要过人验收）。

```
WAT（每周被验收通过的单数）
├─ 供给：在岗角色数 × 单角色周产能
├─ 需求：活跃提单人数 × 人均提单频次
├─ 质量：一次通过率 / 驳回率 / 升级率
├─ 效率：单均人工分钟（验收 + 例外处理）
├─ 经济：单均成本 / 节省额 / 回收期
└─ 信任：高危事故数 / 审计覆盖率 / 记忆命中率
```

### 9.2 四屏看板

| 屏 | 受众 | 核心内容 | 刷新 |
| --- | --- | --- | --- |
| 经营屏 | CEO | WAT、节省人时、单位成本、回收期 | 日 |
| 质量屏 | 主管/质检 | 一次通过率、驳回原因分布、升级率 | 实时 |
| 产能屏 | 平台 | 在岗角色、并发、失败率、模型延迟 | 实时 |
| 风险屏 | 风控 | 越权拦截、超额度、异常角色、审计缺口 | 实时 |

- 成本与风险放右下角，是决策依据，不是装饰。
- 驳回必须选原因码，一次点击，不写小作文。
